Lesson 1: What is Spec-Driven Development?

The methodology that both OpenSpec and SpecKit implement

The Problem: AI Coding Without a Contract

When you prompt an AI coding assistant with "add dark mode to my app," you're starting a negotiation with no agreement. The AI interprets your request, makes assumptions about scope, and produces code. If the result isn't what you wanted, you either iterate through more prompts, manually fix the code, or start over.

This works for small tasks. It breaks down when:

  • Changes span multiple files or services
  • Multiple team members need to understand what was built
  • You need to verify the implementation matches intent
  • You want to revisit decisions weeks later
Key Insight The fundamental problem isn't AI capability — it's alignment. Without an explicit contract, human intent and AI output diverge.

The Solution: Spec First, Code Second

Spec-Driven Development (SDD) flips the traditional workflow. The specification becomes:

  1. A contract — Human and AI agree on what to build before any code is written
  2. A source of truth — Tools use the spec to generate, test, and validate code
  3. Documentation — The spec persists as a record of intent and decisions

The SDD Workflow

Requirements → Design → Tasks → Implementation

The key difference from ad-hoc prompting:

  • Each phase produces artifacts — Written documents, not chat messages
  • Human reviews before implementation — You approve the plan before code is generated
  • Artifacts live in the repo — Version-controlled alongside your code

Static vs Living Specs

Both OpenSpec and SpecKit use static specs — written once, then manually maintained. This is a deliberate trade-off: portability and simplicity over automatic synchronization.

Static SpecsLiving Specs
Manually maintainedAuto-update with code
Can drift from implementationAlways synchronized
Portable, vendor-neutralOften vendor-locked
