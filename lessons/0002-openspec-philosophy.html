Lesson 2: OpenSpec Philosophy & Workflow

Fluid, iterative, brownfield-first

OpenSpec's Philosophy

OpenSpec explicitly states its values:

→ fluid not rigid
→ iterative not waterfall
→ easy not complex
→ built for brownfield not just greenfield
Fluid not rigid
Update any artifact at any time. No strict phase gates.
Built for brownfield
Delta markers (ADDED, MODIFIED, REMOVED) track changes relative to existing code.

The OpenSpec Workflow

/opsx:explore → /opsx:propose → /opsx:apply → /opsx:archive

Explore (Optional)

/opsx:explore is a "no-stakes thinking partner" — reads your codebase, weighs options, helps shape a plan before formal commitment.

Propose

/opsx:propose <change-name> creates all artifacts at once:

openspec/changes/add-dark-mode/
├── proposal.md     # Why
├── design.md       # How
├── tasks.md        # Checklist
└── specs/          # Requirements
Key Differentiator OpenSpec generates all artifacts in one command. SpecKit requires multiple commands.

Apply & Archive

/opsx:apply implements tasks. /opsx:archive moves completed work to archive/ with timestamp.

Delta Markers

OpenSpec's brownfield superpower:

## ADDED Requirements
### Theme selection
The app SHALL let users switch themes.

## MODIFIED Requirements  
### User preferences
Now includes theme selection.

Strengths

  • Low ceremony — One command creates all artifacts
  • Brownfield-native — Delta markers reduce spec size
  • Explore-first — Thinking before committing
  • Clear archival — Completed work moves out of the way

Potential Gaps

  • No constitution/principles (SpecKit has this)
  • No extension system (schemas only)
  • Less granular phase control
