Lesson 3: SpecKit Philosophy & Workflow

Structured, extensible, GitHub-native

SpecKit's Philosophy

SpecKit (GitHub's official SDD toolkit) emphasizes structure and extensibility:

Intent-driven development
Specifications define the "what" before the "how."
Multi-step refinement
Each phase is a distinct command with its own artifact.
Extensibility by design
Extensions, presets, and bundles allow deep customization.
Constitution-first
Project principles are established before any feature work.

The SpecKit Workflow

/speckit.constitution → /speckit.specify → /speckit.plan → /speckit.tasks → /speckit.implement

Constitution (Once per Project)

/speckit.constitution establishes project-wide principles that guide all work. Unique to SpecKit.

Specify → Plan → Tasks

SpecKit separates concerns across commands:

  • /speckit.specify — What to build (requirements)
  • /speckit.plan — How to build it (tech stack, architecture)
  • /speckit.tasks — Actionable breakdown
Key Differentiator SpecKit separates "what" from "how." OpenSpec combines them in a single propose.

The Extension System

SpecKit's major differentiator:

ComponentPurposeExample
ExtensionsAdd new commandsJira integration
PresetsCustomize templatesCompliance format
BundlesRole-based packsSecurity researcher
 
# Install extension
specify extension add jira-integration

# Install bundle
specify bundle install security-researcher

Strengths

  • Constitution — Project-wide principles
  • Granular phases — Clear separation of concerns
  • Extension system — Deeply customizable
  • Converge command — Built-in reconciliation
  • 125k GitHub stars — Massive community

Potential Gaps

  • More ceremony (multiple commands)
  • No explore phase (clarify is structured, not conversational)
  • No built-in archive state
  • Greenfield-optimized (less brownfield tooling)
  • Python dependency (heavier setup)
