Glossary

Spec-Driven Development terminology for OpenSpec and SpecKit

Core Concepts

Spec-Driven Development (SDD)
A methodology where specifications are written before code, serving as the source of truth for both humans and AI agents. The spec becomes the contract that guides generation, testing, and validation.
Specification (Spec)
A structured document describing what to build and why, independent of implementation details. Contains requirements, acceptance criteria, and constraints.
Living Spec
A specification that automatically updates as implementation evolves, staying synchronized with the actual codebase. Contrast with static spec.
Static Spec
A specification that remains fixed after creation, requiring manual updates when implementation diverges. Both OpenSpec and SpecKit use static specs.
Spec Drift
The divergence between a specification and actual implementation over time. A key challenge with static specs that both tools attempt to mitigate.
Artifact
A document or file produced during the SDD workflow. Examples: proposal, design, tasks, requirements.

OpenSpec Terminology

Change
OpenSpec's unit of work. Each change gets its own folder under openspec/changes/ containing all related artifacts (proposal, specs, design, tasks).
Proposal
The "why" document. Captures the reason for a change, what's affected, and impact. Created via /opsx:propose.
Delta Marker
OpenSpec's notation for tracking changes: ADDED, MODIFIED, REMOVED. Indicates how requirements relate to existing functionality.
Explore
OpenSpec's discovery phase via /opsx:explore. A "no-stakes thinking partner" that reads code, weighs options, and shapes a plan before commitment.
Apply
Implementation phase via /opsx:apply. Executes the tasks defined in the change.
Archive
Completion phase via /opsx:archive. Moves the completed change to openspec/changes/archive/ with timestamp.
Store (Beta)
OpenSpec's cross-repo planning feature. A separate repo containing specs shared across multiple implementation repos.

SpecKit Terminology

Constitution
SpecKit's project principles document. Created via /speckit.constitution, it defines governing guidelines that shape all subsequent development.
Specify
Requirements phase via /speckit.specify. Defines what to build focused on the "what" and "why", not tech stack.
Plan
Technical design phase via /speckit.plan. Adds implementation details: tech stack, architecture, patterns.
Tasks
Breakdown phase via /speckit.tasks. Generates actionable task list from the plan.
Implement
Execution phase via /speckit.implement. Builds the feature according to the plan.
Converge
Reconciliation via /speckit.converge. Assesses codebase against spec/plan/tasks, appending remaining work as new tasks.
Clarify
Optional phase via /speckit.clarify. Identifies underspecified areas before planning. Formerly called "quizme".
Extension
SpecKit plugin that adds new commands and capabilities beyond the core workflow.
Preset
SpecKit customization that modifies how existing commands behave (templates, terminology, formats).
Bundle
SpecKit package combining extensions, presets, and workflows for a specific role (e.g., product manager, security researcher).

Workflow Phases

Phase OpenSpec SpecKit
Discovery /opsx:explore /speckit.clarify
Requirements /opsx:propose /speckit.specify
Design (included in propose) /speckit.plan
Task Breakdown (included in propose) /speckit.tasks
Implementation /opsx:apply /speckit.implement
Completion /opsx:archive (manual)

Spec Formats

EARS (Easy Approach to Requirements Syntax)
A structured notation: WHEN [condition] THE SYSTEM SHALL [behavior]. Used by Kiro; informally influences both OpenSpec and SpecKit.
Given/When/Then (Gherkin-style)
Scenario format: GIVEN [context] WHEN [action] THEN [outcome]. Common in both tools for acceptance criteria.
Capability
OpenSpec term for a coherent unit of functionality. Specs are organized around capabilities, which can be ADDED or MODIFIED.

Technical Terms

Greenfield
A new project with no existing codebase. Both tools support greenfield, but SpecKit's full workflow is optimized for it.
Brownfield
An existing codebase with established patterns. OpenSpec's delta markers and change-focused workflow are designed for brownfield.
Slash Command
AI assistant invocation like /opsx:propose or /speckit.specify. The primary interface for both tools.
Agent-Agnostic
Works with multiple AI coding assistants. Both OpenSpec (25+) and SpecKit (30+) claim broad compatibility.
